# AI 常见反模式 · functional-flow

> 这些是 AI 在本步骤（绘制功能流程）中最容易犯的错误。PM 审查时遇到以下模式应直接进入 Revision 修改确认。

## AP1：只画主流程当全流程
- **表现**：每个 FEA 只有"起点→成功"，没有分支流程、异常流程
- **为什么有害**：开发实现时只覆盖主路径，分支与异常场景全部漏掉；测试无异常用例可写
- **修复**：每个功能流程至少补 1 条分支流程与 1 条异常回退路径

## AP2：裸分支无条件标签
- **表现**：决策点引出两条箭头，却不写"什么情况下走哪条"
- **为什么有害**：图"看起来全"，实则分支不可执行、不可测试
- **修复**：每条分支标注具体判定条件；条件须互斥、可穷举

## AP3：复合动作压成一步
- **表现**："填写并提交"、"选择并确认"压成一个方框
- **为什么有害**：隐藏了确认、校验、二次提交等真实业务步骤，下游无法挂接规则
- **修复**：把复合动作拆成可独立实现的步骤

## AP4：为让流程"完整"而发明步骤
- **表现**：上游功能清单/故事没有的业务步骤，AI 为了补全而自行加上
- **为什么有害**：范围蔓延；用户/产品被"看起来很顺"的图误导
- **修复**：自补步骤标 `AI_INFERENCE`，列入手工确认清单，绝不冒充 FACT

## AP5：把跨系统交接画成普通节点
- **表现**：与第三方/库存/支付系统的交接点，画得与内部步骤无异
- **为什么有害**：下游误以为交接必成功，无失败回退设计
- **修复**：交接节点标注系统边界、传递数据、失败回退目标

## AP6：用规则/状态明细冒充流程
- **表现**：图里写"密码必须 8 位""仅 VIP 可见""库存不足禁止下单""提交后状态机转已确认"
- **为什么有害**：功能流程图混入校验、权限、状态机与异常处理明细，层次不清；规则归 business-rules/validation-rules、状态归 state-machine、异常明细归 exception-handling
- **修复**：流程只保留"到哪个业务步骤、怎么判定、去向哪里"

## AP7：异常路径缺失却标 ready_for_human_review
- **表现**：失败、超时、取消、恢复路径未覆盖，仍把状态标为可评审
- **为什么有害**：人类评审被"完整"误导，实则在补测试漏洞
- **修复**：异常路径缺失时标 `needs_user_input` 或 `conditional_review`，列明缺口

## AP8：把 IX / BR / STATE / EX 写进流程图
- **表现**：图里写"点击后弹窗""密码必须 8 位""订单状态机流转""支付失败提示语"
- **为什么有害**：结构层与规则层边界污染，下游子技能无法分工
- **修复**：命中交互/校验/权限/状态/异常处理的细节即移交，图中只留"到某步骤/某分支/某回退目标"
