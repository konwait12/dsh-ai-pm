# 人类审查清单 · 异常与失败处理

> 本清单给 **PM/业务方** 在审查 AI 产出的父文档 `function-description.md` §2 各 FUN 的「异常与失败处理」小节时使用。
> 不是给 AI 看的（AI 看 `audit-checklist.md`）。
> 每条 = "是 / 否 / 不适用"，有"否"则进入 Revision 修改确认。

## 正确性
- [ ] 失败场景是否真实？「余额不足」「活动已结束」等失败是否与业务方/线上证据一致，而不是 AI 猜的？
- [ ] 恢复策略（重试/回滚/补偿/终止）是否是业务方认可的决策？还是 AI 擅自决定的？
- [ ] 每条 `EX-XXX` 的来源 SRC-* 是否引用正确？监控/工单/纪要的位置与关键内容是否与原文一致？

## 完整性
- [ ] 每个 P0 `FUN-XXX` 是否至少有一条 `EX-XXX`？高风险的函数（涉及金钱、库存、外部依赖、数据）是否覆盖了对应的失败分支？
- [ ] 六类失败源（校验/权限/资源/业务/冲突/网络）是否按该函数真实风险排查过？有没有明显该写但没写的失败？
- [ ] 每条 EX 是否都有用户可见提示？有没有「沉默失败」或只写内部错误码的行？

## 一致性
- [ ] `触发条件` 与 `系统行为` 是否分开写、语义一致？（不会出现「条件写超时、行为却写余额不足」的错位）
- [ ] `用户提示` 与 `恢复路径` 是否一致？提示说"请重试"，系统实际有没有重试逻辑？
- [ ] 可恢复失败与不可恢复失败是否区分清楚？不会让用户对不可恢复的失败反复点击重试？

## 可测性
- [ ] 每条 `触发条件` 是否可判真伪？开发/测试能否不看实现就复现这条失败并验证系统行为？
- [ ] 重试策略是否有明确边界（次数/间隔/幂等/是否需人工介入）？不是「重试一下」这种空话？
- [ ] 如果我是接手这个需求的开发/测试，按 EX 表能否构造出每个失败分支来验证恢复？

## 可维护性
- [ ] 金钱/库存/数据类失败是否有补偿或回滚路径？补偿自身的失败是否也有兜底？
- [ ] 有没有出现实现细节（try-catch、异常类型、超时毫秒数、消息队列、幂等键）混在产品语义里？

## 可追溯性
- [ ] 每条 `EX-XXX` 是否可追溯到所属 `FUN-XXX` 与来源文档？`AI_INFERENCE` 是否明确标记、`UNKNOWN` 是否登记到待确认？
- [ ] 与 `BR` 异常分支、`ST` 异常路径、`VL` 校验拒绝是否有关联？下游 `AC` 能否覆盖每条 EX 做验收？

## 最终判断
看完这份异常处理产出后，回答这两个问题：
1. **你认同这些失败都会真实发生、且恢复策略正确吗？** 如果有不认同的失败分支或策略，缺什么证据或决策？
2. **开发/测试拿到这张 EX 表能否无歧义地实现并验证每一个失败分支？** 如果不能，哪些行还需要补充？
