# AI 常见反模式 · 异常与失败处理

> 这些是 AI 在本子技能中最容易犯的错误。PM 审查时遇到以下模式应直接进入 Revision 修改确认。
>
> 注：示例统一使用通用业务场景（订单支付、库存扣减等），避免与 `test/skills/` 下的测试夹具业务域同域，防止误导。

## AP1：一条兜底异常走天下
- **表现**：所有 FUN 都只写「系统异常，请稍后重试」，权限/冲突/资源不可用全部省略
- **为什么有害**：下游无法对不同失败做差异化恢复，等于没写
- **修复**：按六类失败源（校验/权限/资源/业务/冲突/网络）逐函数排查，只写真实可能发生的，不可能发生的标注「不适用」

## AP2：触发条件不可判定
- **表现**：写「当系统繁忙时」「视网络情况」等无法复现的表述
- **为什么有害**：测试和开发拿到后只能猜，无法写自动化测试分支
- **修复**：触发条件必须可判真伪，能写进 `VL-` 校验或测试分支（如「当提交时余额不足导致扣款失败」）

## AP3：触发条件与系统行为混写
- **表现**：一行里既写失败又写处理（「提交超时了然后提示重试」）
- **为什么有害**：无法独立审查「什么失败」与「系统做什么」
- **修复**：一行一个事实：条件（什么失败）→ 行为（系统做什么），分开写

## AP4：有提示无恢复
- **表现**：只写「系统提示错误」或「提示用户稍后重试」，不说明重试边界
- **为什么有害**：用户不知道要不要再试；系统可能实际上没有重试逻辑
- **修复**：恢复路径落到重试/手动/自动/终止之一，写明次数、间隔、是否幂等

## AP5：可恢复与不可恢复混为一谈
- **表现**：可重试失败与需要人工介入的失败共用一条提示
- **为什么有害**：用户分不清该不该再试，可能无限点击或反复失败
- **修复**：不可恢复失败明确终止并引导人工处理，与可恢复失败分开提示

## AP6：金钱/库存失败无补偿
- **表现**：扣款失败、库存超卖只写「提示失败」，不回滚/不补偿
- **为什么有害**：涉及金钱/库存/数据的失败没有补偿事务，会造成资损与数据不一致
- **修复**：金钱/库存/数据类失败必须写明补偿或回滚路径

## AP7：AI 推断的失败冒充事实
- **表现**：AI 猜的失败分支直接写进表里，不打标签、不登记待确认
- **为什么有害**：后续确认时找不到任何一条结论的来源，决策基于未经验证的失败假设
- **修复**：每条 EX 打 `FACT` / `DECISION` / `AI_INFERENCE` / `UNKNOWN`；推断登记到「待确认问题」

## AP8：把实现细节写进产品语义
- **表现**：表里出现 try-catch、异常类型、超时毫秒数、消息队列、幂等键
- **为什么有害**：产品语义与实现纠缠，下游无法复用；违反子技能边界
- **修复**：只写产品级行为与恢复路径；实现细节留给研发
