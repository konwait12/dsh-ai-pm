# Source Handling · 异常与失败处理

## Source Register

为每个失败相关来源分配稳定 ID 并记录：

```text
source_id
title_or_description
format            # 线上监控 / 缺陷记录 / 客服工单 / BRD 异常章节 / 会议纪要 / 接口文档
author_or_speaker
provided_by
created_at
retrieved_at
authority_scope    # 能确认「失败发生」还是「恢复策略」
location_or_link
notes
```

使用 `SRC-001`、`SRC-002` 递增编号。线上监控与缺陷记录能确认「失败真实发生」，属于 `FACT` 观察；恢复策略是业务决策，需要 `DECISION`。

## Extraction Rules

1. 先原样提取失败陈述，再归一化解释。
2. 对每条材料性失败声明保留来源位置与作者。
3. 区分「明确写出的失败」与「隐含的风险」——隐含风险标 `AI_INFERENCE`，不冒充事实。
4. 排除的材料性内容（如"该失败不在本期"）记录一句排除原因。
5. 永远不把"来源没提"当作"该失败不存在"；未确认的失败分支标 `UNKNOWN`。

## Authority And Conflicts

评估来源权威性，不预设通用优先级：

1. 本项目明确的人工确认；
2. 对该业务事实/恢复策略的决策权（业务 owner 拍板恢复策略，研发只能提供技术建议）；
3. 来源的直接程度（一手接口行为 vs 二手转述）；
4. 时效性及后声明是否显式取代先声明；
5. 独立来源相互印证。

当来源冲突：

- 保留双方陈述与来源 ID；
- 说明每种解读的影响；
- 识别可能的事实/决策 owner；
- 若改变材料性结论，标记 `conflict` 并停下，绝不静默选更方便的一方。

## Research Boundary

仅当外部事实能实质性改进失败处理理解且可查证时做研究（监控数据、缺陷系统、公共平台错误码语义）。记录来源、日期、事实/推断状态、置信度、适用性与决策影响。

研究不能确认内部业务策略（恢复策略、补偿范围、可接受风险）。这些提交给有决策权的人。

## Mixed Media

- 缺陷记录 / 客服工单：保留单号、现象、频率、已有人工补救（人工补救 = 系统缺口信号）。
- 线上监控：记录指标口径（P99 还是平均值）、时间窗口、样本量。
- 接口文档：只作为失败触发条件的佐证，不作为恢复策略来源。
- 会议纪要：区分「明确的失败描述」（FACT）、「讨论中的方案」（ASSUMPTION/AI_INFERENCE）与「已拍板的决策」（DECISION）。
