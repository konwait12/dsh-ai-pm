# Exception Handling 思考框架

> **Common Core（必用）**：先应用 `src/framework/thinking-core.md` §1 的 6 个通用 lens（第一性原理 / 系统思考 / 对抗性审查 / 逆向验证 / 确认偏误防御 / 知识边界认知），再应用本文件领域透镜；Audit 前应用 §2 校验层（事前验尸 / 空杯视角 / 可测试性 / 结论先行 / 读者视角）。只记录改变候选内容的发现，不重复粘贴分析。

产出高质量异常处理的思考方式：不做「给每个函数随便编一条系统异常」，而是做「失败源的系统性枚举与差异化接住」。
先枚举失败点，再锁定可判定的触发条件，再定义系统行为、恢复路径与用户提示，最后自检边界与可追溯性。
每个镜头都附带一个自问句与一个典型反模式，写之前先照一遍。

## 镜头 1：失败源枚举（Failure Source Enumeration）

问题：这个函数的每一次失败点我都枚举了吗？还是只写了最明显的一种？

- 对每个 P0 `FUN-XXX`，按六类失败源逐类排查：校验失败、权限失败、资源不可用、业务规则违反、数据冲突、网络错误。哪个在本函数真实可能发生就写，不可能发生的显式标注「不适用」而非略过。
- 失败要落到"这个函数的具体失败"（如"余额不足导致扣款失败"），不是笼统的「系统异常」。
- 反模式：每个函数只写一条「系统异常，请稍后重试」，把权限、冲突、资源不可用全部省略，下游无法针对不同失败做差异化恢复，等于没写。

## 镜头 2：触发条件可判定（Trigger Condition Determinability）

问题：这条异常在什么条件下触发？条件能被测试与开发无歧义地复现吗？

- `触发条件` 必须可判真伪，可写进 `VL-` 校验或自动化测试分支，例如「当提交时校验必填字段缺失」「当并发修改同一记录导致版本冲突」。
- 触发条件与系统行为分开写，一行一个事实：什么失败（条件）、系统做什么（行为），不混在一起。
- 反模式：写「当系统繁忙时」「视网络情况」这类不可判定表述，或把触发条件揉进系统行为里，开发拿到后只能猜。

## 镜头 3：恢复路径与用户提示（Recovery Path & User Prompt）

问题：每次失败都有明确的恢复路径和用户可见的提示吗？可恢复与不可恢复分开了吗？

- `恢复路径` 落到重试 / 手动 / 自动 / 终止四类之一，并写清边界：重试次数与间隔、是否幂等、是否需人工介入。不可恢复的失败要明确终止并引导人工处理，而不是含糊地"提示一下"。
- `用户提示` 是面向用户的中文自然语言，说明「哪里失败了 + 用户能怎么办」，不是内部错误码或「请联系管理员」。
- 反模式：只写「系统提示错误」而不写恢复路径，或写「提示用户稍后重试」却不说明重试边界；可恢复与不可恢复失败共用一条提示，用户分不清该不该再试。

## 镜头 4：边界保持（Boundary Preservation）

问题：我写的是「失败如何接住与恢复」，还是泄漏到了校验 / 状态机 / 交互 / 实现层？

- 只写异常与恢复：校验"是否拒绝输入"属于 validation-rules，重试"状态如何流转"属于 state-machine，UI 如何提示属于 interaction-rules，都不在此处展开。
- 表里出现字段格式、正则、try-catch、超时毫秒数、消息队列、幂等键等字样即为越界，立刻移除或降级为一句恢复路径的边界描述。
- 反模式：把异常处理写成实现说明书，混入校验规则与技术选型，导致产品语义与实现细节纠缠、下游无法复用。

## 镜头 5：可追溯性与知识状态（Traceability & Knowledge State）

问题：这条失败场景与恢复策略凭什么成立？是事实、用户决定、推断还是未知？

- 每条 `EX-XXX` 结论打上 `FACT` / `DECISION` / `AI_INFERENCE` / `UNKNOWN`；推断与未知必须同步登记到「假设、AI 推断、未知与冲突」章节，不得在表中伪装成事实。
- 每条 `EX-XXX` 可反追溯到 `FUN-XXX` 与来源文档；用户提示文案与恢复策略的语义保持一致，无「提示重试但系统不重试」的矛盾。
- 反模式：把 AI 推断出的失败场景直接当事实写进表里、不打标签、不登记待确认，后续确认时找不到任何一条结论的来源。

## 稀疏降级模式（Sparse Degradation Mode）

当失败源稀少——只有一句「给下单加个异常处理」，没有已确认的业务规则 / 状态机 / 校验结果可支撑失败分支时，上面的五个镜头无法产生有意义的产出。对不足信息强行套用镜头只会产出冗长而空洞的 EX 表。切换降级模式：

```text
low-density input → 跳过全部镜头发散
                   → 不进入 Generate / Audit
                   → 只输出：
                      a) 输入充分度评估（涉及哪些 FUN？六类失败源中哪些已有确认证据？）
                      b) 一批澄清问题（每个：AI 初步判断 + 选项 + 影响 + owner）
                   → status = needs_user_input
                   → 等人工补足后，以充分模式重新进入 Preflight
```

降级触发（满足任一即可）：

- 没有已确认的失败来源（无 business-rules / state-machine / validation-rules 支撑）
- 用户只提到功能或做法（「加个异常处理」「失败时提示一下」），没有任何失败场景或恢复要求
- 失败处理被想当然地假定（「系统会提示错误」）而无任何策略

此模式不是失败状态，而是对信息不足的正确响应——产出一批干净的澄清问题，而不是一张编造的 EX 表。

## 确认偏误防御（Confirmation Bias Defense）

异常处理是 AI 最容易顺着「用户只说 happy path」往下写的地方：

1. 我是不是只写了用户提过的失败，而漏掉了该系统真实高风险的失败分支？
2. 我有没有把 AI 猜的失败场景当 FACT 写进表里？
3. 用户说「系统会提示」，我有没有替他把恢复策略也编出来？

## 知识边界认知（Knowledge Boundary）

1. 是否区分「来源确认的失败」（FACT/DECISION）与「我推断的失败」（AI_INFERENCE）与「没人知道」（UNKNOWN）？
2. 无法确认的恢复策略 / 提示文案是否登记到待确认，还是埋进表格 prose？
3. 失败处理的总量与函数风险量级是否匹配——函数多而异常为零，或所有函数共用一条兜底异常，都是危险信号。
