# Audit Checklist · exception-handling

每次提交给父级 function-description 前自审。先跑确定性校验器（`scripts/validate_artifact.py`），再逐条过本清单。
异常处理产出的是"会失败的事 + 系统怎么接住"，逐条检查是否覆盖、可判定、有恢复路径、有用户提示、且不越界。

## 1. Structural Gate（结构门：章节存在、ID 前缀齐全）

- [ ] 父文档 `function-description.md` 中存在 `## 2. 分功能详述` 章节，且异常处理内容位于各 `FUN-XXX` 块内的「异常处理」小节，无游离在函数块之外的孤儿异常
- [ ] 至少存在一条 `FUN-\d+` 标识（校验器 `ID_PATTERN = r"FUN-\d+"`），异常场景以 `EH-\d+` 编号，无缺失、无重复、无跳号
- [ ] 每条 `EH-XXX` 都挂在某个 `FUN-XXX` 之下，与函数职责一一对应
- [ ] 表头列与模板一致：`ID | 异常场景 | 触发条件 | 系统行为 | 恢复路径 | 用户提示 | 来源`
- [ ] `python3 scripts/validate_artifact.py <function-description.md> --json` 返回 `"ok": true`

## 2. Content Gate（内容门：异常处理产出是否完整且正确）

- [ ] 每个 P0 `FUN-XXX` 至少有一条 `EH-XXX`；P1 函数按需覆盖，无遗漏也无空壳占位
- [ ] 六类失败源（校验失败、权限失败、资源不可用、业务规则违反、数据冲突、网络错误）已按该函数的实际风险逐个排查，不是所有函数都套用同一条"系统异常"
- [ ] 每条 `EH-XXX` 的 `触发条件` 可判真伪（能写进自动化测试的分支），未写「当系统繁忙时」「视情况」等不可判定表述
- [ ] 每条 `EH-XXX` 都写明 `系统行为`：失败发生后系统具体做什么（拦截、降级、回滚、阻断），未留空
- [ ] 每条 `EH-XXX` 都写明 `恢复路径`：重试 / 手动 / 自动 / 终止，且标注边界（重试次数、间隔、是否幂等、是否需人工介入）
- [ ] 每条 `EH-XXX` 都有面向用户的 `用户提示` 文案，为中文自然语言，说明「哪里失败了 + 用户可以怎么办」，不是系统内部错误码
- [ ] 可恢复失败与不可恢复失败已区分：可恢复的给重试/自动路径，不可恢复的明确终止并引导人工处理，未混为一谈
- [ ] 异常场景与函数真实职责一致，未凭空编造失败分支，也未遗漏该函数已知的高风险路径

## 3. Boundary Gate（边界门：内容不泄漏到其他子技能）

- [ ] 未重新定义字段格式/必填/正则等校验规则（→ validation-rules `VL-XXX`）
- [ ] 未写领域计算、约束、权限判定等业务规则（→ business-rules `BR-XXX`）
- [ ] 未写重试的状态流转、转移条件与副作用状态机（→ state-machine）
- [ ] 未写 UI 呈现层内容（按钮、弹窗、toast、loading、hover）与交互反馈（→ interaction-rules `IX-XXX`）
- [ ] 未写可度量的验收用例 Given/When/Then（→ acceptance-criteria `AC-XXX`）
- [ ] 未引入实现层细节（try-catch、异常类型、超时毫秒数、消息队列、幂等键等工程实现）
- [ ] 与 validation-rules / state-machine 边界清晰：只写"失败如何接住与恢复"，校验"是否拒绝"与状态"如何流转"分别归属上游子技能

## 4. Semantic Gate（语义门：知识状态、可追溯性）

- [ ] 每条 `EH-XXX` 标注来源：可回溯到 `FUN-XXX` → `FEA-XXX`/`ST-XXX`，且场景内容与来源确认的失败描述一致
- [ ] 知识状态正确打标：业务方/来源确认的失败场景标 `FACT` 或 `DECISION`；AI 推断出的失败分支标 `AI_INFERENCE`，未冒充事实
- [ ] 无法确认的恢复路径或用户提示标 `UNKNOWN` 并登记到父文档「待确认问题」，不静默编造
- [ ] `恢复路径` 与 `用户提示` 在语义上一致：提示告诉用户的路与恢复策略实际走的路吻合，无「提示重试但系统不重试」的矛盾
- [ ] 异常总量与函数风险量级匹配——函数多而异常为零，或所有函数共用同一条兜底异常，都是危险信号

## 5. Human Gate（人工门：可以提交）

- [ ] 阻塞性确认项（影响恢复策略、用户提示文案等关键失败场景）均已有明确答案，非阻塞项已注明原因
- [ ] 无 `待确认` 残留在已确认的异常行内；仍有占位的内容已降级为 `UNKNOWN` 并给出负责人
- [ ] 下游子技能（state-machine 重试流转、acceptance-criteria 异常用例）可无歧义地消费本产出
- [ ] 与父级编排约定一致（按 `P0 FUN` 驱动、在 state-machine 之后产出），无越权写入
- [ ] 本子技能产出已同步回父文档 §2 各 `FUN-XXX` 的「异常处理」小节，且未改动其他小节
