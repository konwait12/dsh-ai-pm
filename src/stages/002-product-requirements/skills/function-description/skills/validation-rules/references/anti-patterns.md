# AI 常见反模式 · 系统校验（validation-rules）

> 这些是 AI 在本子技能中最容易犯的错误。PM 审查时遇到以下模式应直接进入 Revision 修改确认。
>
> 注：本文示例统一使用通用业务场景（内容平台、企业服务、电商），避免与 `test/skills/` 下的测试夹具业务域（招聘网站、设备预测性维护、客户邀约活动等）同域，防止误导。

## AP1：校验规则不可判定
- **表现**：写"校验手机号格式"、"金额不能太大"、"长度要合理"而不给出可执行值域
- **为什么有害**：开发无法实现、测试无法构造用例，等于没写
- **修复**：给出具体值域（正则/区间/长度/必填），无法判定就标 UNKNOWN 并提问

## AP2：编造取值口径
- **表现**：AI 自己定"密码必须 8 位"、"手机号只支持大陆"，未标 `AI_INFERENCE`，当作业务事实写进 VL
- **为什么有害**：业务方误以为已确认，后续可能拒绝合法数据或放行非法数据
- **修复**：取值口径必须有出处（BR/码表/安全策略/字段定义），否则标 AI_INFERENCE + 待确认

## AP3：错误提示写开发向内容
- **表现**：提示写成 `Invalid input`、`E002`、`该字段违反唯一性约束`，或含糊到用户不知道要改成什么
- **为什么有害**：提示是产品体验的一部分，用户看不懂就无法修正，客服压力转移
- **修复**：中文自然语言，说明哪里错 + 期望值 + 怎么改，区分失败类型

## AP4：漏掉隐藏输入
- **表现**：只对"看得见的表单框"写校验，漏掉 URL 参数、可被改写的默认值、批量粘贴/上传数据
- **为什么有害**：非法数据从非表单路径进入系统，绕过所有校验
- **修复**：枚举完整输入面（表单/筛选/上传/批量/URL 状态参数），逐个覆盖

## AP5：给只读/系统字段写校验
- **表现**：对系统自动生成的字段（如优惠金额、创建时间）写校验
- **为什么有害**：永远不会触发的规则是噪音，还会让下游误以为这些字段可被用户输入
- **修复**：只校验用户输入面；系统生成字段标记"不需校验"

## AP6：过度校验堵死合法业务
- **表现**：把校验写得太严（如金额上限误拒合法大额订单、名称拒绝合法特殊字符），没有豁免通道
- **为什么有害**：合法业务值被拒，业务方投诉"系统不让我干活"
- **修复**：校验边界与业务方确认；必要时提供白名单/豁免路径并记录决策

## AP7：跨字段约束缺失或自造
- **表现**：只写单字段独立校验，A 必填当且仅当 B 被选择的依赖缺失；或反过来自造与被引用 BR/UX 矛盾的跨字段规则
- **为什么有害**："单查都通过、联查就崩"；自造规则破坏可追溯性
- **修复**：跨字段约束与 BR/字段定义对齐；有矛盾标 CONFLICT 提交裁决

## AP8：校验来源缺失成孤儿
- **表现**：VL 不挂 FUN-XXX、不引 BR/字段定义，取值口径无出处
- **为什么有害**：下游无法追溯"凭什么"，校验变成无主声明
- **修复**：每条 VL 挂到对应 FUN 块，来源列可追溯；孤儿 VL 删除或归位
