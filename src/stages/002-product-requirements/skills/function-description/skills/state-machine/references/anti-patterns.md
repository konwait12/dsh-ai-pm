# AI 常见反模式 · 状态机（state-machine）

> 这些是 AI 在本子技能中最容易犯的错误。PM 审查时遇到以下模式应直接进入 Revision 修改确认。
>
> 注：本文示例统一使用通用业务场景（内容平台、企业服务、电商），避免与 `test/skills/` 下的测试夹具业务域（招聘网站、设备预测性维护、客户邀约活动等）同域，防止误导。

## AP1：只写主流程、漏掉非成功路径
- **表现**：只画「提交→审核→通过」主链路，漏掉取消、超时、驳回后重提、回退、并发等分支
- **为什么有害**：实现时对非成功路径凭空猜测状态去向，线上产生脏状态
- **修复**：按"当前状态 × 事件"矩阵穷举，覆盖成功/失败/取消/超时/重试/回退/并发

## AP2：悬空转移与非法转移留空
- **表现**：某状态遇到某事件时目标态不写；终态回退这类被禁止转移留空（等于默认允许）
- **为什么有害**：实现方按"默认允许"处理，生命周期失去约束
- **修复**：每个组合都有目标态；被禁止的转移显式标「不允许」并给原因

## AP3：守卫条件不可判定
- **表现**：写"当订单异常时自动驳回"、"合适时机推进状态"，没有可判定的表达式
- **为什么有害**：开发无法判断何时触发，测试无法构造用例
- **修复**：守卫写成可判定表达式（时间/数值/角色/状态），无法判定则标 UNKNOWN 并提问

## AP4：副作用悬空
- **表现**：写"通知相关人员"——谁、什么渠道、什么时候全空；联动更新、审计、回滚遗漏
- **为什么有害**：下游无法接线通知与联动，实现方自行发挥
- **修复**：副作用点名到具体对象；无副作用显式写「无」

## AP5：把 UI 视图或实现细节当状态
- **表现**：把「按钮变灰」「列表页」写进状态表；混入表结构、消息队列、幂等实现
- **为什么有害**：产品语义与界面/工程纠缠，下游无法复用状态定义
- **修复**：状态=实体生命周期条件；UI 展示→interaction-rules，实现→工程层

## AP6：把 AI 推断的流转当事实
- **表现**：AI 推断"审核超时 30 分钟自动驳回"，未标 `AI_INFERENCE`，直接写进转移表
- **为什么有害**：业务方误以为已确认，后续可能接受错误的生命周期行为
- **修复**：推断转移标 `AI_INFERENCE` 并登记待确认；来源确认过的才标 FACT/DECISION

## AP7：终态语义矛盾
- **表现**：终态之后还能回到进行中（"取消后还能重新发货"），或取消/终止语义不一致
- **为什么有害**：生命周期不闭环，实现与验收混乱
- **修复**：识别终态并显式定义"能否重开"；取消与终止语义统一

## AP8：与业务规则冲突
- **表现**：BR-007 禁止某转移，状态表却允许；或状态表定义的守卫与 BR 不一致
- **为什么有害**：规则与状态机互相矛盾，下游各实现各的
- **修复**：每条转移引用其约束 BR-XXX；冲突标 CONFLICT 提交裁决，裁决后回流更新
