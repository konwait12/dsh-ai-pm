# 人类审查清单 · 状态机（state-machine）

> 本清单给 **PM/业务方** 在审查 AI 产出的 §状态变化（STATE-XXX）时使用。
> 不是给 AI 看的（AI 看 `audit-checklist.md`）。
> 每条 = "是 / 否 / 不适用"，有"否"则进入 Revision 修改确认。

## 正确性
- [ ] 状态列表是否就是业务方真实的状态集合？有没有杜撰的状态或漏掉真实状态（如取消、超时、驳回后重提）？
- [ ] 每条转移的守卫条件（如"超时 30 分钟未支付"）是否与业务方确认的口径一致？
- [ ] 触发事件是否命名准确？同一个事件在不同状态下是否有不同的去向？

## 完整性
- [ ] 每个状态对每个可能触发事件是否都有去向？有没有"有触发器但没写目标态"的悬空转移？
- [ ] 是否覆盖了取消、超时、重试、重复提交、回退、并发等非主成功路径？
- [ ] 起始态、中间态、终态是否都被识别并标注？终态之后还能不能回来？

## 守卫与副作用
- [ ] 每条守卫条件是否可判定？有没有"视情况 / 适当时候 / 合适时机"这类词？
- [ ] 副作用是否点名到具体对象（谁、什么渠道、什么时候）？没有副作用是否写了「无」？
- [ ] 被禁止的转移（如终态回退）是否显式标注，而不是留空白让开发自己猜？

## 一致性
- [ ] 状态机与业务规则 `BR-XXX` 是否一致？有没有被 BR 禁止、状态表却允许的转移？
- [ ] 状态命名是否全库统一？「待审核 / 审核中」这类易混状态是否会造成歧义？
- [ ] 与异常处理（exception-handling）的分界是否清楚：异常只作为转移条件/副作用点到为止？

## 可追溯性
- [ ] 每条转移是否可追溯到 `BR-XXX` / `IX-XXX` / 已确认故事？
- [ ] AI 推断的转移是否标注 `AI_INFERENCE`，没有冒充 `FACT`？
- [ ] 未定的状态语义是否已进入父文档「待确认问题」并给出责任人？

## 最终判断
看完这份状态机后，回答这两个问题：
1. **这套生命周期是否就是你业务里的真实状态流转？** 有没有一条转移会让真实业务走不通？
2. **你可以直接拿这套状态表去给开发实现吗？** 有哪些转移、守卫或副作用还需要补充？
