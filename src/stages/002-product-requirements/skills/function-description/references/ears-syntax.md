# EARS 需求句式参考（EARS Syntax）

> 来源吸收：Trae `ai-prd-writer` skill 的 EARS（Easy Approach to Requirements Syntax）句式与 REQ-ID 分类，适配为 function-description 规则表述的统一句式标准。
> 定位：BR/VL/状态/异常等规则描述使用 EARS 五句式，消除歧义、提升可测试性，与 AC 的 Given/When/Then 互补（EARS 定义规则，GWT 定义验收）。

## 1. EARS 五种句式

| 句式 | 关键词 | 适用 | 示例 |
|---|---|---|---|
| **普遍式（Ubiquitous）** | 陈述句（无关键词） | 恒定不变的事实 | 系统显示设备当前运行参数。 |
| **事件驱动式（When）** | `当〈触发事件〉时` | 有明确触发事件 | 当设备参数超过预警阈值时，系统生成预警记录。 |
| **条件式（If）** | `如果〈条件〉，则` | 有前置条件才成立 | 如果设备处于维护模式，则系统不生成预警。 |
| **状态式（While）** | `在〈状态〉期间` | 特定状态窗口内 | 在维护工单执行期间，系统锁定设备参数修改。 |
| **可选式（As）** | `依据〈能力/数据〉` | 能力或数据可选 | 依据设备历史数据，系统预测下一次故障时间窗口。 |

### 规则

1. **每条规则只用一种句式**，不混用。
2. 条件必须**可判定**：`如果〈布尔表达式〉`，不用「如果合适」「如果必要」。
3. 触发事件必须**可观察**：`当〈可观测事件〉时`，不用「当用户觉得」。
4. 状态必须**有边界**：`在〈状态〉期间`，明确状态进入/退出条件。

## 2. REQ-ID 分类（可选采用）

当功能描述需要细分需求类型时，可用前缀分类替代或补充 FUN-*：

| 前缀 | 含义 | 示例 |
|---|---|---|
| `REQ-FUNC-*` | 功能性需求 | REQ-FUNC-003：设备参数实时展示 |
| `REQ-AI-*` | AI 相关（Prompt/模型行为） | REQ-AI-001：预警文本生成 |
| `REQ-DATA-*` | 数据/接口需求 | REQ-DATA-002：传感器数据接入 |
| `REQ-NFR-*` | 非功能需求 | REQ-NFR-007：响应时间 P95 ≤ 2s |

> 项目默认仍以 `BR-*` / `VL-*` / `AC-*` 为主 ID；REQ-* 前缀仅在规则数量大（≥ 20 条）或需跨类型追溯时采用，避免 ID 体系膨胀。

## 3. 与现有契约的关系

- **BR/VL 规则**：正文使用 EARS 句式（`当/如果/在/依据`），保持 BR-XXX / VL-XXX ID。
- **AC 验收**：仍用 Given/When/Then（见 acceptance-criteria 子 Skill），GWT 的 when 从句可直接复用规则的事件驱动式。
- **状态迁移**：状态式（While）适用于 state-machine 子 Skill 的状态窗口描述。
- **异常处理**：事件驱动式（When）最常用——`当〈异常〉时，系统〈响应〉，用户〈看到〉`。

## 4. 正反例对照

```markdown
❌ 模糊（无句式）：
  设备异常时应该给出合理的提示，方便用户处理。

✅ EARS 事件驱动式：
  当设备离线超过 30 秒时，系统在监控看板显示「设备离线」状态标记，并在设备详情页提供「重新连接」按钮。

❌ 条件不可判定：
  如果条件合适，系统允许用户修改预警阈值。

✅ EARS 条件式：
  如果当前用户角色为「设备管理员」，则系统允许修改预警阈值；否则阈值输入框置灰。
```

## 5. 评审 Checklist

- [ ] 每条规则使用 EARS 五句式之一（当/如果/在/依据/普遍式）
- [ ] 条件可判定（布尔表达式）、事件可观察、状态有边界
- [ ] 无「合理提示」「适当反馈」「视情况而定」类模糊措辞
- [ ] AC 的 when 从句与规则触发条件一致（可追溯）
- [ ] 需要时使用 REQ-* 前缀分类（不默认采用）
