# Thinking Framework · page-design

> **Common Core（必用）**：先应用 `src/framework/thinking-core.md` §1 的 6 个通用 lens（第一性原理 / 系统思考 / 对抗性审查 / 逆向验证 / 确认偏误防御 / 知识边界认知），再应用本文件领域透镜；Audit 前应用 `thinking-core.md` §2 校验层（事前验尸 / 空杯视角 / 可测试性 / 结论先行 / 读者视角）。只记录改变候选内容的发现，不重复粘贴分析。

产出「页面设计」时的思考透镜。逐个透镜提问，规避对应的反模式。停止在"页面骨架"层：视觉、交互微细节、业务规则一律留给下游。

## 1. Entry/Exit lens（入口/出口透镜）

**提问：** 用户如何进入这个页面？进入前必须满足什么前置条件？每个操作完成后用户被带往哪里？

**反模式：** 只从上一页的"下一状态"推导入口，忽略外部直达入口（深链、外部跳转、系统通知），导致入口列与前置条件列空缺；或让操作"原地完成"却不说清结果页，制造悬空状态。

## 2. Content lens（内容透镜）

**提问：** 这个页面承载什么内容？主要信息区块、列表、表单、确认信息各是什么？

**反模式：** 把"主要内容"写成视觉或布局描述（如"顶部放一个大按钮，底部放蓝色卡片"），或堆砌交互微细节；应写"页面上呈现哪些信息、用户在此能看到什么"，而不是"长什么样"。

## 3. Action lens（操作透镜）

**提问：** 用户在页面上能执行哪些操作？每个操作之后的状态是什么（成功/失败/停留/退出）？

**反模式：** 一个页面列了多个操作却没有对应的下一状态，或把"提交→校验→保存→跳转"拆成多个含糊动作合并在一句里，让下游无法判断每个动作的归属和结果。

## 4. State lens（状态透镜）

**提问：** 这个页面的空、加载、部分、成功、失败、超时、权限不符、陈旧数据等状态各自是什么样？各状态会通向哪个页面？

**反模式：** 只画主路径、只写"成功"一种结果；备选、异常、失败、超时、取消、恢复路径的页面没有条目，导致测试与下游无法覆盖。

## 5. Traceability lens（可追溯透镜）

**提问：** 这个页面属于哪个 `FEA-\d+`？对应 `functional-flow`（功能流程）中的哪一步、上游哪个故事？删除它有没有依据？

**反模式：** 凭空新增未在 `functional-flow`（功能流程）出现的页面，或把同一功能的多个页面按"屏幕数"机械拆分；任何页面都必须能向上追溯到功能、流程、故事，否则就是范围蔓延。

## Low-Density Degradation Mode

当上游 `functional-flow`（功能流程）步骤缺失或只有一个模糊页面概念、没有任何流程材料时（见 `SKILL.md` §1 Preflight 判定），五个领域透镜无法产生有效工作。

```text
low-density input → skip 5-lens ideation
                   → do not enter Generate / Audit
                   → output only:
                      a) input sufficiency assessment（页面清单 / 前置条件 / 操作与下一状态的缺失清单）
                      b) batched clarifying questions（每条：AI 初步判断 + 选项 + 影响 + owner）
                   → status = needs_user_input
                   → wait for human to fill in, then re-enter Preflight in sufficient mode
```

Degradation triggers（任一即触发）:

- 只有一句"给 X 做个页面"，没有任何流程步骤
- 上游 functional-flow 未 confirmed 或步骤为空
- 用户要求"设计页面"却无法说清页面数量与用途

这不是失败状态，而是信息不足时的正确响应——省下人工评审时间，产出一批干净的澄清问题，而不是一张满是 `待确认` 的页面表。

## Confirmation Bias Defense（Wave-1 特化）

1. 我是不是在照着需求方口头"想要的页面"设计，而不是照流程推导页面？
2. 需求方的"就是一个普通列表页"是否隐藏了空态、失败态、权限态的页面需求？
3. 我补的每个信息区块/操作，是来自流程证据，还是来自"常见页面长这样"的猜测？

## Knowledge Boundary（Wave-1 特化）

1. "流程里有"（FACT）与"页面通常需要"（AI_INFERENCE）是否可区分？
2. 空态、失败态、权限态这些尚未确认的页面状态，标 `UNKNOWN` 交人工了吗？
3. 前置条件里的数据/权限前提，是我从功能清单推断的，还是已确认的？

在以上透镜全部通过、且未向下游泄漏内容后，才进入提交。每个页面的条目应能被评审者独立理解，无需 AI 现场解释。

## 表达层技法（可选加载）

当 P0 流程 ≥ 3 页、涉及状态分支、或需要多方评审时，加载 `references/prototype-techniques.md`（吸收自 interactive-demo-factory / flow2demo），把页面骨架转成可点击 HTML 原型。**文本规则（§2.1 表格）是权威，原型是 UX 的落地产物，不替代文本；忠于输入，不发明页面与状态。**
