# 人类审查清单 · 项目背景与目标

> 本清单给 **PM/业务方** 在审查 AI 产出的 `background-goal.md` 时使用。
> 不是给 AI 看的（AI 看 `audit-checklist.md`）。
> 每条 = "是 / 否 / 不适用"，有"否"则进入 Revision 修改确认。

## 正确性
- [ ] 来源是否正确引用？SRC-001/002/003 的材料位置和关键内容是否与原始材料一致？
- [ ] §4 问题的具体表现和数据（如"480h 停机"、"¥3,800 万损失"）是否与业务方提供的数字一致？
- [ ] §1 需求来源中的人名、角色、时间是否准确？

## 完整性
- [ ] 原始材料中是否有被 AI 遗漏的需求点？（逐份检查原始邮件/纪要/PPT）
- [ ] §5 目标是否覆盖了业务方真正关心的所有维度？有没有"明显应该写但没写"的目标？
- [ ] §6 角色与利益相关者是否完整？有没有遗漏的部门/角色？
- [ ] §8 初步边界中"不包含"的列表是否准确？有没有应该包含但被排除的？

## 一致性
- [ ] §3（现状）和 §4（问题）是否自洽？现状中描述的做法与问题中描述的痛点是否对应？
- [ ] §5 目标和 §4 问题是否对应？每个核心问题是否都有对应的目标？

## 可测性
- [ ] §5 每个目标是否有可衡量的成功判断？（数字/百分比/时间/比率）"提升体验"这类空话是否存在？
- [ ] 如果我是接手这个需求的开发/测试，看完 §5 是否知道"做到什么程度算成功"？

## 可维护性
- [ ] §12 来源追溯是否覆盖了全部原始材料？有没有无来源的"事实"声明？
- [ ] §9 事实与决定中，FACT 项是否都有 SRC 来源？AI_INFERENCE 项是否明确标记？

## 可追溯性
- [ ] §13 下游输入摘要能否让 `user-journey-and-stories`（用户旅程与用户故事）直接使用？角色列表和生命周期线索是否足够？
- [ ] 如果有需要排除的原始材料内容，§12 是否注明了排除原因？

## 最终判断
看完这份产物后，回答这两个问题：
1. **你认同这个项目要做吗？** 如果认同，基于产物的哪些事实和目标？如果不认同，缺什么？
2. **你可以直接拿这份产物去和业务方/技术方开会吗？** 如果可以，哪些部分还需要补充？如果不可以，缺什么？
