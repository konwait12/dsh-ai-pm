# AI 常见反模式 · PRD 汇总

## AP1：在汇总阶段新增需求
- **表现**：PRD 中出现了上游 confirmed 产物中没有的功能描述、新故事、新规则
- **为什么有害**：`prd-assembly` 的唯一职责是"汇总已确认内容"。新增需求绕过了前四步的审查闸门，未经确认就进入了最终 PRD
- **修复**：发现缺失必须回到受影响的步骤重跑（变更回流），不能在 PRD 步骤直接补

## AP2：静默解决不一致
- **表现**：同一个角色在 `project-background-goal` 叫"内容编辑"，在 `user-journey-and-stories` 叫"内容运营"，AI 在 PRD 中统一为一个称谓但未记录
- **为什么有害**：上游的矛盾被隐藏了，后面的读者不知道曾经有过歧义
- **修复**：所有不一致必须记录到 §9 不一致报告，由人工决定如何处理

## AP3：RTM 填假数据
- **表现**：§6 RTM 中所有矩阵项都标记为"已覆盖"，但实际检查发现链条是断裂的
- **为什么有害**：RTM 是交付前的最后一次质量检查。假数据让所有闸门形同虚设
- **修复**：RTM 必须逐条验证。断裂的必须标记，孤儿元素必须列出

## AP4：改写上游已确认内容
- **表现**：AI 觉得上游某段的表述不够好，在 PRD 中"润色"了措辞，但改变了原意
- **为什么有害**："润色" = 未经确认的修改。前四个工作事项 的 confirmed 状态意味着原文已经过人工确认，AI 无权修改
- **修复**：PRD 引用 = 原文照搬。如果需要修改，必须回到原步骤走 Revision 修改确认流程

## AP5：忽略下游读者
- **表现**：PRD 写得像内部工作文档，充满了 Skill 术语（如"§13 下游输入摘要"里的 YAML 格式原始保留）
- **为什么有害**：PRD 的读者是业务方、技术负责人、测试负责人——他们不需要知道模板的内部结构
- **修复**：PRD 是"可交付文档"，应该以最终读者的视角组织内容。模板字段是内部工具，不是最终表达
