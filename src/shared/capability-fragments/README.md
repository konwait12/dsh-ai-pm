# 通用能力片段库（capability-fragments）

> 跨案例重复出现的「通用能力 / 组件型功能」标准片段库。生成 `function-description` 时，组件型/通用型功能**优先引用片段而非重写**；每个片段可追溯到来源案例，杜绝多案例各自重新描述同一能力的重复劳动。
>
> **来源案例字段说明**：片段中标注的 `REQ-XXX`（如 REQ-004/007/006/008）为**历史溯源**，仅用于追溯片段口径的原始证据；新场景复用片段时可直接沿用标准 BR/AC/EX 行，**无需替换**来源案例编号，只需按目标案例校准细则（见 §二.2）。

## 一、用途

1. **复用而非重写**：订阅授权、评论验证、时间选择器等能力在多个跑测案例（REQ-004/007/006/008）中重复出现且各自描述不同，本库沉淀为标准 BR/AC/EX 行，生成时直接引用、按案例校准。
2. **满足规则密度**：组件型 FUN（时间选择/级联/点赞等）天然规则不足（BR < 3 触发 rule_density HIGH 告警），片段自带 ≥3 条标准 BR 兜底（规避规则密度不足）。
3. **来源可追溯**：每个片段标注来源案例与原始 BR/AC/EX ID（如「源 REQ-007 BR-027」），转正式产物时可回溯到真实 BRD 证据。

## 二、使用约定

### 1. 何时引用（适用判定）

| 片段类型 | 触发信号 | 示例 |
|---|---|---|
| 组件型功能 | 功能名/描述是 UI 组件或交互控件 | 时间选择器、级联选择、渠道选择、点赞组件 |
| 通用型能力 | 同一能力在多案例重复出现，行为与校验规则可标准化 | 微信订阅通知授权、评论与昵称验证、分享卡片/海报 |

案例特有业务规则（如某案例独有的 10 分钟定时规则）**不入库**，作为扩展行随片段按需启用。

### 2. 怎么用（复制到 function-description）

1. 将片段中 `FUN-XXX` 改为目标产物实际 FUN 编号（如 FUN-009）。
2. BR/AC/EX ID 改为目标产物内单调递增编号（如 BR-018 起顺延），避免与既有行冲突。
3. 「来源」列保留 `capability-fragments/<file>` 路径，并可追加原始 SRC 追溯（如 `SRC-001 B03`）。
4. 按目标案例 BRD 校准细则：字符上限、默认值、范围声明、模板文案、知识状态（FACT/DECISION/UNKNOWN）。
5. 不适用的行删除并注明原因（Inquiry Gate 处理），不静默丢弃。

### 3. 知识状态与合规

- 片段行默认标 FACT（来自已跑测案例 BRD）；含 UNKNOWN 的行（如鉴黄服务方）必须登记 Q-XXX 由业务方确认，不得视为事实。
- 转正式产物（ready_for_human_review / confirmed）前，由业务事实负责人复核片段口径是否符合该案例。
- 片段行不得伪造来源：新增片段必须标注来源案例与原始 ID，无来源不得入库。

### 4. 维护约定

- 新片段文件命名：`<kebab-case-能力名>.md`，沿用本库「标准 BR 行 / 标准 AC 行 / 标准 EX 行 / 说明」结构。
- 新增/修改片段后，更新下方片段清单表。
- 片段变更不影响任何校验器与回归测试（纯 Markdown 知识库）；但片段被复制进产物后，产物仍走既有 gate 校验。
