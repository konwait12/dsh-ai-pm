1. 这个脚手架帮你做什么

一句话：它是你和 AI 协作写 PRD 的流程控制器——AI 负责起草，你负责拍板，每一步都有机器闸门保证「AI 不能替你确认任何业务事实」。

你只需要做三件事：把材料放进去、用自然语言指挥 AI、在关键节点拍板。产出的是一份经你（和业务方）真实确认、每条声明可追溯的中文 prd.md。

1.1 它解决什么问题：三个最大的坑

AI 写需求文档，最大的风险不是「写得慢」，而是下面三个坑——每个坑都配有「没有这个脚手架会怎样」的真实场景：

风险没有这个脚手架会怎样（反面例子）
① 推断冒充事实
AI 分不清「材料里写了的」和「我自己猜的」		AI 读会议纪要时顺口补了一句「预计转化率提升到 5%」，纪要里根本没有这个数字。没有脚手架，这句话会被当成业务方承诺写进 PRD，研发照此排期，业务方看到时一脸茫然：「我什么时候说过 5%？」
② 没有人明确拍板
需求从没被真正确认过		AI 一口气写完了整份需求文档，文档开头写着「已确认」。其实没有任何人认真看过它。研发按这份「假确认」开工，做出来的东西跟业务方的真实想法差了一截，返工一个月，还互相甩锅「文档上就是这么写的」。
③ 改了上游，下游不知道
需求变了，旧版本还在到处流通		业务方把目标从「提升留存」改成「提升拉新」，但 PRD 和功能描述还挂在旧目标上。研发拿着旧 PRD 做功能，验收标准对不上新目标，全链路追溯断掉，没人发现——直到上线后数据对不上。

脚手架的应对是一对一的：六态标注让推断现出原形（AI 推断只能被当建议看待，永远冒充不了事实）；不可绕过的人工闸门让确认必须由真实评审人批准（机器永远只能产出「待评审」）；变更闭环让上游一变、下游立刻失效并回流重跑（不再有「过期的真相」）。

1.2 它由哪些部分组成

  • 19 个 Skill（5 主 + 9 子 + 4 分支产物 + 1 能力）：5 个主干 skill 是必做主线——project-background-goal（项目背景与目标）→ user-journey-and-stories（用户旅程与故事）→ product-ux（产品 UX）→ function-description（功能描述）→ prd-assembly（PRD 汇总）。9 个子 skill 挂在两个主干下面细化（product-ux 内：page-design / interaction-rules；function-description 内：feature-list / functional-flow / business-rules / validation-rules / state-machine / exception-handling / acceptance-criteria）。4 个分支产物 skill 按需触发（competitive-research、feasibility-analysis、tracking-plan、issue-record），另 1 个能力：requirement-restate（需求重举 · 复述 + 发散双模式，过程记录不进 PRD）。每个 skill 都自带标准章节执行协议、7 类参考知识库和机器校验器，数量全部来自注册表 workflow-registry.json（唯一真相源）。
  • 18 个脚本（在 src/scripts/）：pipeline.py（命令入口：init / status / entry / gate / review / reflow）、orchestrator.py（状态机 + 信号层）、dor_check.py（闸门检查）、workflow_registry.py（注册表访问器）、consistency_check.py（跨文档一致性）、traceability_check.py（双向追溯）、property_check.py（逻辑完备）、branch_validator.py（评审记录与哈希校验）、migrate_layout_v2.py（布局迁移）、audit_log.py（SHA-256 链事件日志）、projection_cache.py（投影缓存）、registry_contract_check.py（注册表契约关卡）、validation_errors.py（统一错误格式）、hash_anchor.py（哈希锚点）、desensitize_check.py（脱敏检查）、feishu_fetch.py（飞书取料）、prd_publish.py（飞书发布）、snapshot_cases.py（快照对比）。全部只用 Python 标准库，AI 不需要装任何第三方包。
  • 9 个共享机制（在 src/shared/）：audit（审查闸门）、human-gate（人工闸门）、clarify（澄清循环）、change-management（变更回流）、traceability（追溯）、decision-log（决策记录）、brainstorming（需求发散）、intake-routing（入口路由）、project-init（项目初始化）。它们横向服务所有阶段，是脚手架的「公共服务」。

2.1 Claude Code：主力执行者

推荐作为「干活的那一个」。它打开项目会自动读 AGENTS.md 启动协议；起草、跑校验、解释报错都交给它。安装与打开方式：

2.2 Codex CLI：验收 / 检查 / 方案判断

Codex 在这个项目里的角色不是「再来一个写稿的」，而是独立的检查方。这个项目推荐的分工是：Codex 负责检查、验收、计划、方案判断、风险识别、需求澄清和最终把关；Claude Code 负责按明确计划做执行（起草、跑命令、结构性修改）。具体用法：

  • 检查与验收：Claude Code 起草完一个产物，让 Codex 独立读一遍，对照 AGENTS.md 的硬红线逐条给结论——两个人做、两个人查，避免「自写自审」。
  • 方案判断：A / B 两个方案怎么取舍，让 Codex 从影响范围、成本、风险角度先做一轮分析，你拿它的分析去拍板。
  • 风险识别：让 Codex 专门找「这个需求里最容易被忽略的三个风险」，多一双眼睛看。
  • 需求澄清与最终把关：正式确认之前，让 Codex 复核「待拍板事项是不是列全了」，防止漏掉关键决策就送审。
用法示例：Claude Code 写完产物后，你对 Codex 说：「检查 requirements/REQ-NNN 的产物是否满足 AGENTS.md 的全部硬红线，逐条给结论，不要修改任何文件。」

2.3 Cursor / Copilot：IDE 内看代码、小修改

适合在 IDE 里打开产物文件、看某一段内容、改一句话。它们不擅长跑长流程（8 步循环、多轮确认），所以不要把「完整跑一个需求」交给它们——那个活让 Claude Code 干。

2.4 模型怎么选：三原则

原则例子：该用 / 不该用
① 复杂步骤用最强推理模型该用：需求起草、澄清提问、冲突判断、PRD 汇总——想错了后面全错，值得用好档位（如 Claude 的 Opus 级别）。
不该用：用便宜快模型起草关键的用户旅程，漏了异常分支，最后整段重做，反而更贵。
② 机械步骤可以用快模型该用：建目录、跑校验脚本、查状态、复制模板——不需要深度推理，快模型足够也省钱。
不该用：让最强模型反复跑 status 查状态，纯属浪费。
③ 同一个工作项内别换模型该用：一个工作项从起草到确认，用同一个模型做完，上下文连续，六态标注和追溯链不会断。
不该用：起草用 A 模型、打回修改换 B 模型——B 不知道之前问过哪些问题，会重复提问、改坏标注。

2.5 验证 Agent 是否合格（三硬要求各配验证方法）

4. 第一次打开：让 AI 先读说明书

4.1 AGENTS.md 是什么

AGENTS.md 是给 AI 的工作合同——它规定 AI 在这个项目里能做什么、不能做什么、按什么顺序读文件。它是任何 AI 执行体（Claude Code / Codex / Cursor / Copilot / 其他）进入项目的第一份必读文件。不读合同的 AI 会把需求文档乱写一通、或者自己假装确认过——这两件事正是这个项目最不能容忍的。所以打开项目后，先让 AI 读说明书再开工，没有例外。

4.2 让 AI 读的完整口令

你：请读项目根目录的 AGENTS.md，按里面的启动顺序把 5 个框架文件都读一遍
   （workflow-registry.json → constitution.md → workflow.md → thinking-core.md → contracts.md），
   然后用三句话告诉我：这个项目是干什么的、边界是什么、哪些事你永远不能做。

注意口令里的三要素：① 读 AGENTS.md ② 按启动顺序读 5 个框架文件（顺序不许乱）③ 用三句话复述。「三句话复述」是验证——不是读了就算，是读懂了才算。顺序为什么重要？注册表定义路径、宪法定义红线、工作流定义步骤、思考核心定义方法、契约定义标注——乱序读会得出矛盾的结论。

4.3 好的复述长什么样

正例（就位了）：「这是 PRD-only 产品经理脚手架，把原始需求材料逐步转成经人工确认的中文 prd.md。边界是：我不做研发任务拆分、技术架构设计、测试用例、API 合约。我永远不能：① 自己设置 confirmed ② 上游未确认就启动下游 ③ 在 PRD 汇总阶段新增需求。我已按启动顺序读完了 5 个框架文件。」
反例（没就位）：「好的，这个项目是写 PRD 的，我准备好了，你想先写哪部分？」——没提启动顺序、没提 5 个文件、没提任何红线，甚至没确认自己读没读 AGENTS.md。这种回答等于没读。

4.4 如果 AI 没读就开干：怎么识别、怎么纠正

怎么识别——出现以下任一信号，说明它在没读说明书的情况下硬干：

  • 你问「读了吗」，它说「读了」却说不出启动顺序和任何一条红线；
  • 不盘点材料，上来就写产物内容；
  • 说出「我已经确认了这个需求」或「我直接批准了」——这个项目里 AI 永远没有这个权限；
  • 跳步：背景目标还没确认，就开始起草用户旅程。

怎么纠正——一条口令打断并重置：

"停。你还没进入工作状态：现在按 AGENTS.md 的启动顺序读 5 个框架文件，
 读完复述三条硬红线给我听。确认理解之前，不要写任何产物。"

等它复述到位再继续。为什么必须做这一步：这一步花 2 分钟，省后面 2 小时——不读合同的 AI 会用错误的方式把整个需求流程带偏。

5. 怎么给 AI 下指令（核心）

记住一句话分工：AI 是起草者，你是事实与决策的唯一来源。所有指令都围绕这个分工展开。这一章是全教程最值得反复读的一章。

5.1 指令四原则（每条约 2 个正例 + 1 个反例）

原则 ① 给材料——永远让 AI 从你给的材料出发，不让它凭空发挥：

  • 正例 1：「我把会议纪要和邮件放进 00-input 了，你登记成 SRC 来源，从这些材料起草。」
  • 正例 2：「材料里没有的信息不要补，标成未知来问我。」
  • 反例：「你随便写写这个需求的背景吧。」——「随便」= 让 AI 自由发挥 = 编造材料。

原则 ② 指定工作项——一次只说一件事，指明工作项名：

  • 正例 1：「现在做 project-background-goal（项目背景与目标）这一步。」——AI 会自己读对应 SKILL.md 并按 8 步循环执行。
  • 正例 2：「上一个工作项确认完了，继续下一个：user-journey-and-stories（用户旅程与故事）。」
  • 反例：「帮我做做背景、旅程还有功能啥的。」——一次甩三件事，顺序和依赖全乱，产物会互相污染。

原则 ③ 要结果清单——规定 AI 每步完成必须汇报什么：

  • 正例 1：「完成后告诉我：产物路径、校验结果、待我拍板的事项、下一步建议。」
  • 正例 2：「跑完校验把每条 FAIL 都贴出来，别只说『有点问题』。」
  • 反例：「做好了叫我。」——它可能闷头写很久，把待决策项全吞了。

原则 ④ 禁止越权——AI 的权限边界要随时盯：

  • 正例 1：「产物只推到待评审状态，确认由我来。」
  • 正例 2：「不确定的就标 UNKNOWN 挂问题清单，别替我做决定。」
  • 反例：「你确认没问题就直接过了吧。」——把确认权交给 AI，等于让它伪造人工确认，这是违反宪法的行为。
红线：任何一步，如果 AI 想跳过你的确认往下走（比如背景目标还没确认就开始写旅程），立即说「停下，先把上一步给我确认」。

5.2 「要结果清单」模式：AI 每步必须汇报四件事

这是全教程最重要的习惯：给 AI 下任何长指令，都把它必须汇报的内容钉死。四件事：

汇报项含义例子
① 产物路径写完的文件在哪，方便你打开看requirements/REQ-NNN/001-business-requirements/01-background-goal/background-goal.md
② 校验结果机器闸门过没过、哪几条没过gate：5 项检查 4 过 1 FAIL（六态缺 UNKNOWN）
③ 待拍板事项哪些事只有你能决定（问题编号）Q-001 目标数值待你确认；DEC-001 是否支持线下核销待你拍板
④ 下一步建议它建议接下来做什么（仅供参考，决定权在你）建议：你确认背景目标后，继续用户旅程与故事
万能模板：「完成后按四件事汇报：产物路径 / 校验结果 / 待我拍板的事项 / 下一步建议。缺一不可。」——背下来，几乎适用所有步骤。

5.3 什么话不该说（模糊指令反例集）

  • 「你看着办」——把决策甩给 AI，等于把 DECISION 的帽子戴在 AI 头上。
  • 「尽快 / 大概 / 差不多就行」——模糊词会让 AI 放低校验标准，六态标注也会偷懒。
  • 「把这些都写了」——不指明哪些、按什么顺序，AI 只能猜，猜就是推断冒充事实的源头。
  • 「按行业惯例来」——行业惯例是 AI 的推断，不是你的决定；你的项目有自己的业务事实。
  • 「你确认过了就可以」——确认权是你的，这句话是无效授权，还会误导 AI 违反宪法。

5.4 长任务的拆法：一次只做一个工作项

一个需求有 5 个主工作项，每个都有人工闸门。正确节奏是「一步一步走，每步确认完再迈下一步」：

第一步：project-background-goal（背景与目标）→ 你确认
第二步：user-journey-and-stories（旅程与故事）→ 你确认
第三步：product-ux（产品 UX）→ 你确认
第四步：function-description（功能描述）→ 你确认
第五步：prd-assembly（PRD 汇总）→ 你确认

每步之间可以间隔很久（等业务方确认），这不影响流程——status 命令会告诉你当前停在哪、下一步是什么。想让 AI 一次「把整个需求做完」？可以，但它每完成一个工作项仍然会停下来等你确认——这不是它偷懒，是硬性流程：上游未确认，下游不启动。

6. 一个需求从零到 PRD 的完整剧本

以「客户邀约活动系统」为例（编号 REQ-NNN），把 5 幕拆成「你说 → AI 做 → 你确认」的完整对话。每一幕结尾都有一个「你确认」的节点——那是流程的呼吸点，也是你唯一要说「批准」的地方。

第 1 幕 · 开工（初始化 + 材料登记 + 入口判定）

你说：

"帮我初始化一个新需求，编号 REQ-NNN，主题是客户邀约。
 然后把我的材料放进 00-input，跑一下入口判定，告诉我成熟度。"

AI 做：建好需求骨架目录（含授权清单和来源登记表），把材料登记成 SRC-001、SRC-002…，跑 entry 判定。如果材料只有想法，它会说：「entry 判定结果：L0 仅想法，材料不足。建议先跑需求重举（发散模式）——我把候选列出来，你来处置。」

你确认：要么补材料，要么说「好，先发散」——等候选清单出来后，你人工勾选 include（进入需求）/ exclude（排除）/ defer（延后）/ research（待研究）。只有 include 的候选进入背景目标的输入包。

第 2 幕 · 业务需求（背景目标 → 旅程故事）

你说：

"按 project-background-goal 工作项起草，用我 00-input 里的材料，
 不确定的地方列成 ≤5 个问题问我，别自己编。完成后按四件事汇报。"

AI 做：走 8 步循环（预检 → 摄取 → 思考 → 澄清 → 生成 → 审计 → 人工闸门 → 提交）起草 background-goal.md，每条声明带六态标注，然后汇报：「产物已起草：…/background-goal.md。这里整理了 3 个事实（来自 SRC-001）、2 个假设、1 个未知（目标数值）——需要你拍板。gate 校验：5 项检查 4 过 1 FAIL（六态缺 CONFLICT），我补上了。下一步建议：你确认后我做用户旅程。」

你确认：读产物 → 回答那 ≤5 个问题（不会答的让它标 UNKNOWN 挂问题清单）→ AI 修订重跑校验 → 你看没问题后亲自跑确认命令（命令见第 7 章）→ 说「继续做 user-journey-and-stories」。

你说（第 2 幕后半）：

"继续 user-journey-and-stories：用户旅程地图、用户故事集、范围基线，
 全部从已确认的背景目标推导，不要引入新事实。"

AI 做：起草 journey-and-stories.md（旅程按角色 × 生命周期展开，故事带业务价值），输出 scope-baseline（范围基线）。

你确认：评审 → 亲自 review → 「继续产品 UX」。

第 3 幕 · 产品需求（产品 UX → 功能描述）

你说：

"继续 product-ux：页面设计、交互规则都按上游已确认的内容来，不要新增需求。
 2 个子 skill（page-design、interaction-rules）按顺序跑。"

AI 做：起草 product-ux.md。子 skill 在这里登场——它们不是独立步骤，而是挂在父 skill 产物内部的章节工序，随父 skill 一起跑：page-design（页面设计）产出页面骨架 → interaction-rules（交互规则）产出 IX-XXX 规则，全部汇入 product-ux.md 对应章节。期间它会问：「P03 页面的空态怎么处理？这是 UNKNOWN，我挂到问题清单了，编号 Q-004。」——遇到需要业务状态判断的，它不会替你选。

你确认：评审 product-ux → 亲自 review → 「继续 function-description」。

你说（第 3 幕后半）：

"继续 function-description：功能清单、功能流程、业务规则、校验、状态机、异常、验收，全部要能追溯到上游。
 7 个子 skill（feature-list、functional-flow、business-rules、validation-rules、state-machine、exception-handling、acceptance-criteria）按顺序跑。"

AI 做：起草 function-description.md——feature-list（功能清单 FEA-）→ functional-flow（功能流程：主流程/分支/异常）→ business-rules（业务规则 BR-）→ validation-rules（系统校验 VL-）→ state-machine（状态变化 STATE-）→ exception-handling（异常与失败处理 EX-）→ acceptance-criteria（验收依据 AC-），逐节生成、逐节审计。

你确认：评审 function-description → 亲自 review。

注意：AI 在每一幕送审前都会做一件必须的事——B3 收口。它会告诉你：「我在问题清单里登记了收口：当前工作项已写入 issue-record 的 §13 收口表。本阶段没有遗留问题，空收口也是审计证据。」 这是送审前的强制动作，缺了它 gate 会拦截送审。

第 4 幕 · 出 PRD

你说：

"汇总 PRD。记住只能聚合已确认的内容，发现缺口就告诉我该回到哪一步补。"

AI 做：prd-assembly 把 4 个上游产物按模板组装成 prd.md（9 节结构见第 1 章 1.3 节），跑双向追溯检查（每一层 G→ST→FEA→FUN→AC 都有人接、无孤儿），汇报：「PRD 已汇总：…/003-prd-output/prd.md，追溯矩阵全绿。发现 1 个缺口：FUN-003 没有对应 AC，需回到 function-description 补。我先标了待确认，编号 Q-007。」

你确认：要么让 AI 回流到上游补齐再重新汇总，要么拍板接受当前状态——然后做 PRD 的最终确认。

第 5 幕 · 变更回流（如果业务变了）

你说：

"业务方把 G2 从 2% 改成了 5%，帮我 reflow 预览下游哪些受影响，我确认后再应用。"

AI 做：先 dry-run 预览影响面：「变更 G2 会级联失效：user-journey-and-stories、product-ux、function-description、prd-assembly 的 confirmed 都会变成 superseded，需要从最早的受影响项重跑。建议回归点：user-journey-and-stories。」 你确认后，它带 --apply 应用：下游失效 → 写 ChangeRecord → next_work_item 回归最早受影响项。

你确认：从回归点重跑相关章节，重新走各幕的确认流程。这就是第 1 章说的「改了上游下游不知道」——在这个流程里不存在。

7. 只有你能做的事（AI 永远不能替你做）

四件事是「不可委托」的——委托出去，项目的信任基础就塌了。每一件都配「具体怎么做」。

① 登记评审人

在哪：需求目录下的 requirements/REQ-XXX/00-input/authorized-reviewers.json（init 命令创建骨架时自动生成空模板，默认 {"reviewers": []}）。

长什么样（示例 JSON）：

{
  "reviewers": [
    {
      "id": "feishu-uid-8f3a9c21",        ← 稳定用户 ID（飞书或组织 ID），不是昵称
      "name": "王小明",                    ← 真实姓名，跑确认命令时必须一字不差
      "roles": ["business_owner", "product_owner"]   ← 允许批哪些角色
    }
  ]
}

字段什么意思：

  • id：稳定用户 ID（飞书/组织 ID），是程序匹配身份的依据——本地校验以此为准，未来对接飞书/SSO 认证也以它为准；
  • name：真实姓名——跑确认命令时填的名字必须与这里完全一致，写「AI」「待确认」「待评审」或含「模拟」都会被拒绝；
  • roles：该评审人允许使用的角色，可选 business_owner（业务方）/ product_owner（产品方）。每个工作项有自己允许的角色集合（例如 product-ux 只允许 product_owner 批准），你登记了谁、允许哪个角色，谁才能确认。

你可以让 AI 把模板格式建好，但真人信息自己填——「谁有权确认」这个定义不该由 AI 代劳。

② 跑确认命令

AI 完成一个工作项、gate 全绿后，由你亲自跑（也可以让 AI 把命令拼好贴给你，你来执行）：

python3 src/scripts/pipeline.py requirements/REQ-NNN-my-feature review \
  --work-item project-background-goal --decision approve \
  --reviewer "王小明" --reviewer-id "feishu-uid-8f3a9c21" \
  --reviewer-role "business_owner"

每个参数什么意思：

参数意思
requirements/REQ-NNN-…需求目录路径，定位到你要确认的那个需求
--work-item确认哪个工作项：project-background-goal / user-journey-and-stories / product-ux / function-description / prd-assembly
--decision approve批准（把状态写成 confirmed）；写 changes 是打回修改，可附评语
--reviewer你的真实姓名（与 authorized-reviewers.json 完全一致）
--reviewer-id你的稳定用户 ID（与登记一致）
--reviewer-role本次以什么角色批准（必须在该工作项允许的角色集合里）

常见报错（原样认识它们）：

ERROR: a real named human reviewer is required
  → 名字不能是 AI / 待确认 / 待评审 / 含「模拟」，填你的真实姓名

ERROR: reviewer id, name, and role must match 00-input/authorized-reviewers.json
  → 姓名 / ID / 角色三要素与登记表对不上，回去查 ①

ERROR: role business_owner cannot approve product-ux
  → product-ux 只允许 product_owner 角色批——换角色或换有资格的人

ERROR: approval requires ready_for_human_review, got draft
  → 还没到「待评审」状态就急着确认——先让 AI 跑 gate 把产物推到待评审

ERROR: machine gates must pass before approval
  → 机器闸门有未过的项——先修，再确认

③ 业务拍板

AI 会拿一堆「待确认」来找你，你的回答质量决定 PRD 质量。先分清两类问题：

类型例子你的动作
业务事实（只有你能答）目标数值是多少？谁负责核销？线下渠道算不算在内？直接回答；答不上来就让它标 UNKNOWN 挂问题清单（Q- 编号），绝不硬编
技术选择（AI 可以给建议）接口走 REST 还是消息队列？数据存哪张表？让它给选项 + 推荐 + 理由，你了解后拍板；也可以选择不介入（默认采纳推荐）

判据一句话：「这个答案影响业务承诺、成本或验收标准」就是业务事实，必须你拍板；「只是实现方式」可以放权。

④ 最终交付确认

prd.md 确认后，流程还没完，还有三件收尾：

  • 发布：执行发布动作——它由 branch_validator 自动做 SHA-256 复核后产出发布记录，把「这份 prd.md 就是这个版本、就是这份内容」固化下来；
  • 双 Agent 复核：让另一个 Agent（如 Codex）对最终 PRD 做独立验收（做法见第 10 章）；
  • 交付业务方：把 prd.md 和相关评审记录交给业务方收口——最终交付的确认和发布，由你（或授权业务方）完成。

9. 卡住了怎么办（排查顺序）

先记住总原则：任何「卡住」都不是你的错，都是流程在工作。按下面的顺序逐条排查。

9.1 AI 说「被闸门拦住」——三类拦截的真实报错

先让它把 gate 输出逐条贴出来（"gate 拦住了，逐条解释拦什么、为什么、怎么修"）。常见三类，每条都附真实报错原文和修法：

① 入口材料不足（entry_material）——第一项工作项送审前必须至少有 1 份 SRC 材料：

FAIL entry_material 00-input SRC materials: 0 (need >= 1)
→ 修法：把原始材料（纪要/邮件/PPT）放进 00-input 并登记成 SRC-001 起，
  或用需求重举（发散模式）发散出候选。没有材料，背景目标就无从谈起。

② 六态覆盖不全（knowledge_state_coverage）——送审产物必须六态全出现、假设占比不超 30%：

FAIL knowledge_state_coverage missing=FACT,UNKNOWN | covered=4/6 total=12 assumption_ratio=0.25
→ 修法：让 AI 补上缺失的标注——把有依据的标 FACT、把没依据的标 UNKNOWN，
  注意是「补标」，不是「编内容」。
FAIL knowledge_state_coverage ASSUMPTION share 0.40 > 0.30 | covered=6/6 total=15 assumption_ratio=0.40
→ 修法：假设太多，让 AI 把其中能查证的升级成 FACT、需要你定的升级成 DECISION 或 UNKNOWN。

③ B3 阶段收口（stage_closeup）——送审前问题清单必须存在且收口表含当前工作项：

FAIL stage_closeup 99-review/support/issue-record.md 不存在（B3 每阶段强制收口，空清单也是审计证据）
→ 修法：让 AI 建 issue-record.md——即使本阶段没有问题，空清单也要建。
FAIL stage_closeup issue-record 阶段收口表缺 product-ux 收口行
→ 修法：让 AI 在 §13 收口表补上当前工作项的行。
FAIL stage_closeup 1 处「待确认」无 Q-/ISS-/DEC-/SRC- 引用，示例：目标转化率待确认
→ 修法：让 AI 给每个「待确认」挂上问题编号（Q-XXX / ISS-XXX / DEC-XXX / SRC-XXX）。
小结：三类拦截都不是「你要修的东西」，而是「AI 要修的作业」——你把报错贴给它，让它改。

9.2 review 确认命令的报错（你亲自跑命令时会遇到）

  → 名字填成了 AI / 待确认 / 待评审 / 含「模拟」，改填真实姓名。
ERROR: reviewer id, name, and role must match 00-input/authorized-reviewers.json
  → 你不在授权清单里，或名字 / ID / 角色对不上——回第 7 章 ① 检查登记表。
ERROR: role business_owner cannot approve product-ux
  → 角色选错了：product-ux 只允许 product_owner。
ERROR: approval requires ready_for_human_review, got draft
  → 产物还在草稿态，先让 AI 过 gate 推到「待评审」。
ERROR: machine gates must pass before approval
  → 闸门有未过的项（见 9.1），修完再确认。
ERROR: waiver_required issue 'xxx' needs --waive CODE=<reason>
  → 有个可豁免项拦着：你了解风险后显式豁免，命令加 --waive CODE=理由。

9.3 AI 说「我不能确认」

这不是故障，是它做对了。确认只能你来——这正是项目的设计。回应方式：

"好，把产物和待确认事项列清楚：每条标注是哪类（事实/假设/未知/冲突），
 我需要拍板什么、不拍板会怎样。列完我逐条回复。"

9.4 AI 开始编造你没有的材料——识别与打断

识别信号：产物里出现了材料里没有的数字、场景、承诺；或者它说「根据行业惯例 / 我推测」。打断话术：

"停。材料里没有的不要写。这条（指出具体内容）标成 UNKNOWN 挂问题清单来问我，
 我确认后再决定是否进产物。"

9.5 怀疑 AI 跑偏了——对照清单

"现在对照 AGENTS.md 第 3 节「硬红线」逐条检查你自己的行为，每一条给结论：
 ① 有没有设置过 confirmed？② 有没有上游未确认就启动下游？
 ③ PRD 汇总有没有新增需求？④ 每条声明有没有标知识状态？
 ⑤ 产物是不是单点存放？⑥ 变更后有没有让下游失效？
 ⑦ 有没有硬编码路径 / Skill 名？逐条回答，不要跳过。"

9.6 想独立验证 AI 的活

用另一个 Agent（比如 Codex）：「检查 requirements/REQ-NNN 的产物是否满足 AGENTS.md 的红线，逐条给结论，不要修改任何文件。」——两个 Agent 互相制衡，谁都不能自说自话。

10. 进阶玩法

这一章讲四个「更进一步」的能力：分支产物 skill 与能力、信号层、双 Agent 制衡、技法吸收。

10.1 分支产物 Skill 与能力：什么时候触发、对话里怎么触发

分支产物 skill 与能力不占主干，只在触发条件满足时跑，产物默认落在 99-review/support/，不进 PRD 正文。4 个分支产物 + 1 能力的触发条件（来自注册表 trigger 字段）与对话触发方式：

分支产物 / 能力什么时候触发（注册表原文）对话怎么触发
competitive-research（竞品调研）方案方向不清或功能设计缺乏参考"这个功能没有参考，跑竞品调研，3-5 家"
feasibility-analysis（可行性分析）进入主干前评估可行性（市场/技术/投入产出/风险）"进主干前先跑可行性分析，评估市场/技术/投入产出/风险"
tracking-plan（埋点计划）功能需要数据埋点或追踪计划"这个功能要埋点，跑 tracking-plan 出事件表"
issue-record（问题清单）任何阶段需求不明确、冲突或存在风险"把这些问题都登记进 issue-record"（AI 也会主动问你「要不要登记」）
requirement-restate（需求重举 · 能力）材料稀疏 / 多源歧义 / L0 仅想法（entry 机器可判定）"两个材料说法不一致或材料不够，先跑需求重举（复述/发散）核对"

触发前 AI 会问你「要不要跑」——你同意才进。4 个分支产物 skill 的产物：竞品分析（3-5 家）、可行性报告（含 §多方案取舍 DEC-XXX）、埋点事件表 EV-NNN（链 FUN- 与 G-）、问题清单 ISS-NNN（BLK/RSK/DEC/INF/CLS/OUT 六类）；requirement-restate 能力的产物是过程记录（复述清单 RR-NNN 原文 verbatim / 发散候选 SCN-XXX + 四值处置，仅 include 进 bg 输入包）。发布是动作而非 skill：SHA-256 复核由 branch_validator 自动执行。

随时可以问 AI「当前需求有什么信号」——它读的是 orchestrator 的信号层（全部是提示，不会自动执行动作）：

信号含义应对
B1 熔断同一个工作项被连续打回 3 轮 changes——继续打回去大概率还是在老路上打转停下来重新评估修改方向：是不是目标理解错了？材料不够？该跑分支 skill？先对齐再改
B3 老化问题清单里的 open 问题挂起超过 7 天（flag）/ 14 天（escalate）7 天：该找业务方要答案了；14 天：升级处理，别让「未知」躺在清单里烂掉

10.3 双 Agent 制衡：完整流程（起草 → 验收 → 修正循环）

最省心也最符合项目精神的用法——「一个人做、一个人查」：

循环开始
 ① 起草：Claude Code 执行工作项 → 产物推到 ready_for_human_review
 ② 验收：Codex 独立读产物，对照 AGENTS.md 硬红线逐条给结论
       （重点看：六态标注、追溯链、B3 收口、有没有越权/编造）
 ③ 有异议 → 回 Claude Code 修正 → 再跑 gate → 再次让 Codex 复验
 ④ 都通过 → 你亲自 review 确认 → 进入下一个工作项
循环结束

注意 ② 里 Codex 只「检查不修改」——验收方不碰产物，检查结论才干净。第 8 章 ㉑ 条给了现成口令。

10.4 技法吸收：脚手架从外部 skill 吸收的三套技法

脚手架不是从零发明的——它把外部成熟 skill 的技法「吸收」进来适配成自己的能力（对应 references 文件可查）：

  • 原型两步流程（page-design 的可选落地能力）：先出页面清单经人工确认，确认后才生成单文件 HTML。页面清单从已确认的 product-ux 提取（每行可追溯 FEA/IX/BR），编号 P01 起，你确认覆盖完整后，AI 才生成自包含的交互原型，落盘到 99-review/support/prototype/，命名 [REQ-XXX-功能名]-交互原型-v1.0.html。硬规则：不发明页面、分支必须指向清单内页面、状态依赖目标页先弹确认。
  • 参考图还原（image2html 技法）：输入含 UI 参考图 / 竞品截图时走高保真路径——不得把整张图贴成页面背景，导航、卡片、按钮、表格一律用 HTML/CSS 重建；位图只用于照片、地图、复杂插画、品牌视觉；图标用 SVG。还原时参考图是证据（FACT），但「照图还原的布局是否满足业务」未确认——还原解读必须标 AI_INFERENCE 交你确认；竞品截图登记 SRC-* 进入来源追溯；参考图只提升视觉保真，不改变逻辑保真（不因图发明页面或状态）。
  • PRD 结构参考（prd-assembly 的呈现方法论）：吸收 prd / prd-writer 等 skill 的章节骨架——Executive Summary 三段式、用户故事 + AC 分组、风险分析、验收清单——但只借鉴结构、零内容发明：每一章都必须能指出「上游产物哪一段提供」，指不出来的章节就是空壳，宁缺勿造。支持三个变体：standard（完整版）/ executive（高管版，只留摘要）/ technical（工程师版，全量 AC/BR/IX）——任何变体都只做保留/省略，不新增内容。
