# 产物模板可选章节说明 · 术语表与涉及团队及职责总结

> 本文档说明 `background-goal.md` 与 `prd.md` 模板中两个**可选章节**——「术语表」与「涉及团队及职责总结」——的写法、启用条件与论证来源。
>
> 落地位置：`src/templates/stage-1-business/background-goal.md`（project-background-goal 产物模板，源头摘录）；`src/templates/stage-3-prd/prd.md`（prd-assembly 最终 PRD 模板，§5 按需章节下的聚合落点，见 §五）。
> 各章节均为**可选**章节（BG 标题带「（按需）」），校验器不要求，材料不含对应内容时整节删除或标注"本期不适用"。

---

## 一、为什么加（多案例发现材料常有、产物无落点）

多案例实测（三份飞书文档 + REQ-001~REQ-008 跑测）发现真实材料普遍包含两类信息，但脚手架产物没有承载位置：

1. **名词解释 / 术语表**：几乎每份真实 BRD 都有缩写 / 术语表（如业务线缩写、产品线代号、渠道名等，具体案例见附录 A），是团队沟通与后续所有产物一致性检查的基础。此前术语只能作为 `requirement-restate` §7 术语统一、`business-rules`「Unambiguous」审计项等**流程约束**存在，没有交付物落点，缩写只能「漂」在来源追溯里。
2. **涉及团队及职责**：多系统 / 多业务线协作的 BRD 都会点名团队与职责（如某服务号由多业务线共用、某运营团队，具体案例见附录 A），而 BG 产物 frontmatter 仅 `business_fact_owner / goal_decision_owner / reviewer` 三个确认字段，无法表达「谁负责什么、与哪些环节相关」的职责边界。

以某真实案例为实例（具体案例 ID 与术语见附录 A）：
- 材料侧：其 `00-input` 原始 BRD §二·名词解释 含业务线缩写 / 服务号等多行定义；
- 产物侧：其 `001-business-requirements/01-background-goal/background-goal.md` 没有任何术语落点（15 个必需章节均无术语承载位置）。

两个可选章节即在 BG 阶段（业务需求第一步、材料最贴近原始 BRD 的时刻）为这两类信息提供**可追溯落点**，术语与团队信息从源头即可摘录并逐级流入下游产物（JS / UX / FD / PRD 的一致性检查均可引用）。

## 二、为什么可选不强制（避免结构膨胀与破坏既有案例）

1. **材料不总含这些内容**：不是每份需求材料都有名词解释或团队信息。强制要求会在无对应信息的产物里制造「空章节 + 占位符」，降低产物质量、增加人工确认负担。
2. **避免结构膨胀**：BG 模板已有 15 个必需章节 + Clarifications，主干结构经真实案例验证并受校验器标题清单约束；若强制化会改变既有产物结构，破坏已跑通的案例（产物章节标题由校验器按需检查）。
3. **校验器兼容**：BG 校验器（`validate_artifact.py`）只检查必需标题清单（`REQUIRED_HEADINGS`）的**存在性**，不禁止额外章节；`_normalize_heading` 会剥离标题尾部「（…）」后缀，因此「术语表（按需）」「涉及团队及职责总结（按需）」不与任何必需标题冲突，模板本身仍可通过校验。

因此两个章节都标记「按需」，启用条件写进模板注释：**材料含对应信息才启用，否则整节删除**。

## 三、章节写法与示例

### 3.1 术语表（按需）

- 位置：`## 0. 预检输入充分度判定` 之后、`## 1. 需求来源与触发` 之前（作为正文阅读前置参考）。
- 表格三列：`术语 / 缩略词 | 说明 | 来源`，来源列标 SRC 编号（如 `SRC-001`）。

**示例片段**（依据某真实案例原始 BRD 的「名词解释」表整理，仅作写法示范；具体案例 ID 见附录 A，案例产物未做任何改动）：

```markdown
## 术语表（按需）

仅当 BRD 等输入材料含「名词解释 / 术语表」时启用本节：逐条摘录材料中的术语 / 缩略词定义，不自造、不改写；每条标注来源 SRC 编号。

| 术语 / 缩略词 | 说明 | 来源 |
|---|---|---|
| <缩写 A> | <业务线 A 全称> | SRC-001 |
| <缩写 B> | <业务线 B 全称> | SRC-001 |
| <缩写 C> | <产品线 C 全称> | SRC-001 |
| <服务号> | 服务号 | SRC-001 |
```

写法要点：
- 只摘录材料已有定义（FACT 语义），不做推断或改写；
- 若同一术语跨 SRC 出现不同定义 / 同义词，按 `requirement-restate` §7 术语统一处理，并在「说明」中保留两个 SRC 引用，不静默合并；
- 术语表仅承载「材料原文定义」，不承载 AI 推断的术语约定（推断归 §10 假设 / AI 推断）。

### 3.2 涉及团队及职责总结（按需）

- 位置：`## 6. 用户角色与利益相关者` 之后、`## 7. 时间、约束与依赖` 之前（与角色章节相邻，互为补充）。
- 表格四列：`团队 / 角色 | 职责 | 关联环节 | 来源`，来源列标 SRC 编号。

```markdown
## 涉及团队及职责总结（按需）

仅当输入材料含团队 / 职责信息时启用本节：从材料与角色关系中提取各团队 / 角色的职责边界与关联环节，不推断材料未提及的团队；每条标注来源 SRC 编号。

| 团队 / 角色 | 职责 | 关联环节 | 来源 |
|---|---|---|---|
| 待补充 | 待补充 | 待补充 | SRC-001 |
```

写法要点：
- 职责从材料与角色关系提取，只写材料提及的团队，不推断未提及者；
- 「关联环节」指该团队 / 角色与产物或流程阶段的关联（如 BG / JS 人工确认、素材提供、系统维护、下游对接）；
- 与 §6 用户角色与利益相关者互补：§6 聚焦「与背景 / 目标相关的角色、责任和影响」（个体视角），本节聚焦「团队级职责边界」（组织视角）；
- 与「系统间时序图」配套，可共同表达多系统协作场景。

## 五、PRD 模板的对应按需章节（两个可选章节的最终落点）

`src/templates/stage-3-prd/prd.md`（prd-assembly 最终 PRD 产物模板）在 `## 5. 按需章节` 下同样落地「术语表」与「涉及团队及职责总结」两个按需子章节，承接各上游已确认产物中的术语与团队职责信息：

### 5.5 名词解释 / 术语表

> 占位：`| 术语 / 缩略词 | 说明 |`。从各上游已确认产物中汇总术语 / 缩略词定义，逐条摘录不自造；如无术语可标注"本期不适用"。

### 5.6 涉及团队及职责

> 占位：`| 团队 / 系统 | 职责 |`。汇总各上游产物中涉及的团队 / 系统职责，只写上游已提及的团队、不推断；如无明确职责划分可标注"本期不适用"。

要点：

1. **按需不强制**：两子章节位于 `## 5. 按需章节`（§5）下，prd-assembly 校验器（`validate_artifact.py`）的 `REQUIRED_HEADINGS` 只检查「按需章节」父标题的存在性，不强制任何子章节；新增的 `###` 级子章节**不改变** `REQUIRED_HEADINGS`，模板与既有案例均不受影响。
2. **只聚合不新增**：与 PRD 组装哲学一致，两节内容一律摘录自上游已确认产物，不自造术语、不推断未提及的团队；语义权威参考 `docs/术语表-glossary.md`（术语定义）与 `docs/团队职责矩阵-RACI.md`（角色 / 职责边界 / 人机分工）。
3. **与 BG 模板的分工**：BG（`stage-1-business/background-goal.md`）的「术语表（按需）」「涉及团队及职责总结（按需）」是**源头摘录**（含 SRC 来源列）；PRD 的这两节是**聚合落点**（上游已各带来源追溯，故不重复 SRC 列）。
